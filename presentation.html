Routing protocol for multi-radio sensor networks

RODENT.
Pick the right radio,
message by message.

How a sensor node chooses between WiFi, BLE and LoRa on every packet, with almost no computation and no central controller.

Based on the PhD thesis of Brandon Foubert, Université de Lille, 2021 · Prototype on Pycom FiPy
The problem

No radio is best at everything

WiFi is fast but burns 8× the current of LoRa.

LoRa is thrifty and reaches far, but is ~180× slower.

A classic protocol picks one radio. Then any node that radio cannot reach is simply lost.

The idea

Choose the road per message, not per network

A temperature reading and a fire alarm do not deserve the same road. RODENT lets each message type carry its own requirements vector: how much it cares about energy, cost and speed.

Surveillance rv = 0

Periodic readings. Cheap and frugal wins.

Alarm rv = 1

Rare but urgent. Speed wins, cost does not matter.

Result: the same node can send surveillance over LoRa and the alarm over WiFi, at the same moment.

The setting

Many nodes, several radios, two base stations

Convergecast. Every node sends toward a base station: SW for WiFi, SL for LoRa.

N5 only hears N4, and only over LoRa. A WiFi-only protocol delivers 0 % of its packets.

N3 has a weak WiFi link to the base but can reach N1 by LoRa: two possible roads, two different trade-offs.

Each road has four numbers, one byte each: energy, cost (the theoretical cost of sending a message over that link, not a price), rate and hops. Hops carry weight 0 but break ties and stop loops.

The algorithm · 2

A road is built by hearing a neighbour’s road

N5 hears N4 announce its own best road to the LoRa base (15 · 1 · 20 · 1). N5 adds the cost of the link it heard it on.

Costs accumulate, speed is a bottleneck. Values saturate at 255 so a byte is always enough.

This is plain distance-vector routing, only the “distance” has four dimensions and is judged by weights, not a single number.

The algorithm · 3

No routing messages: roads ride inside data packets

The header costs only +5 bytes per packet. In return the network needs no flooding and no dedicated routing traffic.

The algorithm · 4

Roads expire, links are watched

Beacons

A rarely used road would go stale. When a node has nothing to send, it emits a control packet (empty data) carrying its roads. Base stations beacon too, which proves their link is alive.

Two clocks

7 s without a beacon from a neighbour: the link is declared dead.

14 s without a refresh: the road is forgotten.

(values of the prototype, tunable)

Split horizon

If a packet is addressed to me, the road in its header runs through me. I ignore it. This blocks the classic two-node loop.

Together: a failure is noticed in seconds, bad news spreads, and stale roads disappear by themselves.

The decision · 1

Many roads, conflicting numbers: rank with TOPSIS

A multi-criteria method: the best road is closest to an ideal road and farthest from the worst one.

1. Normalise every column (÷ column norm)

2. Multiply by the weights of the message type

3. Ideal and worst = best and worst value among the candidates

4. Distance to ideal (S⁺) and to worst (S⁻)

5. Score C = S⁻ / (S⁺ + S⁻), highest wins

Two weaknesses

  • Steps 1 and 3 depend on the whole candidate set: adding or removing a road can reorder the others. This is rank reversal.
  • Normalising and finding best/worst costs many operations on a tiny microcontroller.
The decision · 2

Fix the yardstick: bounded normalisation

benefit (rate)
r = x / B+    lower is better (energy, cost)
r = B− / x
v = w · r
ideal = w   worst = 0
S⁺ = √Σ(w − v)²   S⁻ = √Σ v²
C = S⁻ / (S⁺ + S⁻)

Why it works

  • Bounds are constants (e.g. 255 for rate): a road’s score no longer depends on its rivals.
  • The ideal is simply the weight vector: nothing to search for.

Honest limits

What RODENT does not do yet

Link discovery is assumed

The link matrix is static in the prototype; discovering neighbours and measuring their costs is future work.

Convergecast only

Nodes talk to base stations. Node-to-node or downlink traffic needs more.

Overhead

5 extra bytes per packet plus beacons. Worth it for small payloads only if the radios’ cost per byte is low.

Small, indoor test

Six nodes in a lab. Field trials planned in agriculture were cancelled by Covid-19.

To remember

Four ideas, one tiny protocol

1 · Each message type has its own weights, so each gets its own road.

2 · Roads are learned by overhearing neighbours: costs add, speed is the bottleneck.

3 · Bounded TOPSIS ranks with a fixed yardstick: stable order, 38 % faster.

4 · Expiry and beacons make failures heal themselves.

B. Foubert, “Routing in heterogeneous wireless sensor networks”, PhD thesis, Université de Lille, 2021.

The hardware

Meet the Pycom FiPy

A programmable board: a tiny computer with no screen and no keyboard, made to sit inside a sensor and talk over radio.

Tiny

55 × 20 mm, 7 g. It runs on 3.3 to 5.5 V: a USB cable or a small battery is enough.

Five networks on one board

WiFi, Bluetooth, LoRa, Sigfox and LTE-M (cellular). RODENT uses two of them: WiFi LoRa

Programmed in Python

MicroPython, a lean Python for chips. Write a file, copy it to the card, it runs. No compiler.

Made for sensors

Up to 22 pins for sensors (analog, I²C, SPI, serial) and a deep-sleep mode that sips microamps.

The FiPy is now discontinued. The ideas carry over to any ESP32 board with a LoRa chip.

The hardware

What is on the board

1 · ESP32. Dual-core processor, 4 MB of memory. It runs your Python program.

2 · WiFi and Bluetooth. Built into the ESP32: fast, but about 240 mA when transmitting.

3 · LoRa radio. Slow but thrifty (about 28 mA) and long range. A Sigfox radio comes with it.

4 · LTE-M modem. Cellular data. Not used in our lab.

5 · Expansion board. USB for power and code, a reset button, a user button, an RGB LED.
